# Contributing

These rules apply to humans and agents. Follow the setup and command reference in
[README.md](README.md). Before changing a package, also read its `CONTRIBUTING.md`
for package-specific development guidance.

## Tooling and validation

- Mise owns tool selection and the task catalog in `mise.toml`. Pin exact tool
  releases; pnpm's version is declared only in `package.json#packageManager`.
- Pnpm owns dependencies. Declare runtime dependencies in the package that
  imports them; shared development tools live at the root. Use `workspace:*`
  for dependencies between workspace packages.
- Commit `pnpm-lock.yaml`, `mise.lock`, and generated `.mise/locks/` sidecars.
  Refresh tool locks with
  `mise lock node pnpm --platform macos-arm64,linux-x64,linux-arm64` after changing
  tool versions. Sidecars must retain their generated bytes.
- After changing dependencies, run `mise exec -- pnpm install`, then
  `mise run setup` to verify a frozen installation and synchronize hooks.
- Run `mise run check` before submitting changes. CI runs the same task.
  Type checking and tests cover all configured packages; formatting and linting
  cover tracked TypeScript, JavaScript, and JSON/JSONC files.

## Formatting and hooks

Biome owns formatting and lint rules in `biome.json`; `.editorconfig` supplies
shared text-file conventions. Configure your editor's Biome integration to use
the repository's installed version. Lefthook owns file selection in
`lefthook.yml`.

Formatting and lint tasks default to tracked files. Select new or changed files
explicitly with repository-root-relative paths; repeated `--file` arguments are
supported, including from package directories:

```sh
mise run fmt --file packages/pix-websearch/src/index.ts
mise run fmt-check --file packages/pix-websearch/src/index.ts
mise run lint --file packages/pix-websearch/src/index.ts
```

Verify that the expected jobs actually run; an empty selection is a skip, not
evidence that a file passed validation. Markdown, YAML, TOML, and generated
lockfiles are outside the Biome hook file selection.

Pre-commit checks formatting and lint without rewriting files. Hooks invoke
mise explicitly, so make mise available on your editor's Git PATH and run
`mise run setup` before committing.

## Adding an extension

Use `packages/pix-websearch` as a reference for package layout and Pi tool registration:

1. Create `packages/<unscoped-package-name>/package.json`, matching the name after
   the scope (for example, `pix-websearch` for `@ikuma.cloud/pix-websearch`). Use a
   unique `name`, `type: "module"`, and `pi.extensions` pointing to `./src/index.ts`.
   Keep new packages private while developing them.
2. Extend `../../tsconfig.base.json` from the package's `tsconfig.json`; include
   its source, tests, and `vitest.config.ts`.
3. Export a default extension factory from `src/index.ts`. Pi loads TypeScript
   source directly. Declare imported Pi packages as `"*"` peer dependencies and
   pin a development dependency for local validation, as recommended by
   [Pi's package documentation](https://pi.dev/docs/latest/packages).
4. Create a `vitest.config.ts` using `defineProject`, a unique test project name,
   the Node environment, and `src/**/*.test.ts`. The root `test.projects` glob
   discovers the package automatically. Directory-based projects do not inherit
   root test options.
5. Add tests for observable behavior or important integration boundaries.
   Isolate tests from personal Pi configuration and avoid model requests.
6. Document usage, configuration, and user-visible limitations in the package's
   `README.md`. Link to a package `CONTRIBUTING.md` for development, testing, and
   implementation guidance; it should link here rather than duplicate shared rules.
7. Run `mise exec -- pnpm install`, format and lint the new files explicitly,
   then run `mise run check`. Add a package development task to `mise.toml` when
   an interactive Pi launch is useful.

Use strict TypeScript and explicit type-only imports. Add comments for rationale
or constraints that would be costly to rediscover.

## Git workflow

Work on a short-lived branch and open a pull request targeting `main`.
Use simplified Conventional Commits: `type[!]: summary`, where `type` is `feat`,
`fix`, `chore`, `test`, `refactor`, or `docs`. The commit-message hook checks this
format. Explain breaking changes and their migration in the commit body.
